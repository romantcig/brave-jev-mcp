      "A refusal is the single most surprising response shape in this model. Your request succeeds, the HTTP status is 200, and the content array is empty. If your code reads content[0].text the way it always has, it throws an index error on a request that the API considers a complete success. The bug is not in your error handling. It is that the thing you need to handle never looked like an error",
      "## The response that succeeds and says nothing\nStart with the shape, because every mistake here comes from assuming a refusal looks like a failure. It does not.\n\nThe four parts of a refusal response: a 200, a stop_reason, an empty content array, and a category",
      "The status is 200. The stop_reason is the string \"refusal\", and that is the field you branch on, before you touch content. The content array is empty, so any code that reaches into it for text is reading a value that was never populated. The reason for the decline sits in stop_details, under a category key",
      "And the billing is gentle: a refusal that happens before any output streams costs nothing, while one that lands mid-stream bills the tokens already sent, which you then discard",
      "The rule that falls out of this is short. Check stop_reason first, on every response, and never assume content has text in it until you have. A harness that branches on the presence of content instead of on the stop reason can pass ordinary traffic and then throw on a refused request in production",
      "## Four categories, two of them your problem\nThe four are cyber, bio, frontier_llm, and reasoning_extraction. Two of them describe intent that is obviously off-limits: extracting the model's raw chain of thought, or using its output to bootstrap a competing frontier model. The other two are the ones that will surprise you. cyber fires on exploit and intrusion tooling, which means a security team doing authorized red-team work trips it on legitimate tasks",
      "That is why the category matters past the moment of the refusal.
